# Data-retention and deletion matrix

No legal retention period is inferred from a development default. MIPF's responsible data-protection/records owners must approve the purpose, legal basis, event anchor, duration, hold rules and disposal method for each data class. Financial, signed-agreement and audit preservation duties must be reconciled with privacy requests by qualified review.

## Policy and deletion state machine

`src/domain/retention.ts` provides versioned property/document-kind policies. Policies move from DRAFT to APPROVED through a distinct authorized approver; older approved versions become SUPERSEDED. A dry run returns bounded eligible/excluded document IDs, policy references and exclusion reasons without content/filenames. The anchor uses the latest relevant document/application/service transition, preserving post-tenancy retention rather than counting only from upload.

Deletion follows REQUESTED → APPROVED → DELETING → COMPLETED, with FAILED available for controlled retry. Requester and approver must differ. Permission, approved exact policy, duration, inactive application/service, legal holds and immutable evidence references are checked again at sensitive steps. `RETENTION_EXECUTION_ENABLED` is false unless explicitly enabled. Download paths deny deletion-pending/deleted records. The Document hash/version and durable deletion evidence remain as tombstones.

`DocumentLegalHold` records impose/release decisions. Releasing a hold requires an independent authorized reviewer. A completed deletion cannot be undone by imposing a later hold. Configure holds before execution when a dispute, investigation or preservation obligation exists.

## Meaning and limits of deletion

Completion means the eligible encrypted file was removed from the current private storage namespace and the retained database metadata records that disposition. It is not proof of physical erasure from SSD media, host snapshots, backups, email/SMS recipients or external vendors. One shared file-encryption key does not provide per-document cryptographic erasure.

The operator must apply approved backup expiry/object-lock schedules, vendor deletion contracts and restored-data deletion reconciliation. A subject's erasure request can remain held or partly fulfilled where necessary evidence must be retained; staff must record the decision and explain the applicable approved basis. Never mark full account erasure complete merely because one blob was unlinked.
