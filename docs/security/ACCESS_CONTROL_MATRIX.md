# Access-control matrix

Source of truth: `src/domain/access.ts`; object restrictions are also enforced in the domain services. This document records the existing role vocabulary and its limits. New controls must update the code and negative tests before being marked verified. Staff accounts require MFA. A role is scoped to a granted property; possession of a role elsewhere supplies no permission in the selected property.

“Yes” is capability authority inside one property, subject to the service's object, state, separation-of-duty and input checks. It is not permission to edit every column or bypass workflow preconditions. Organisation administration and platform infrastructure access are separate boundaries; property grants alone must not confer cross-client administration.

## Granularity and verification

The current role model includes distinct LEASING_OFFICER, MAINTENANCE_OFFICER and FINANCE_APPROVER grants. FINANCE_APPROVER currently receives the same financial capabilities as FINANCE, with maker-checker enforced by the transaction workflow; it is not an approval-only custom policy. The empty PLATFORM_OPERATOR property role grants no personal-data capability. A separate explicit PlatformGrant permits organisation provisioning/configuration metadata only; organisation/property grants are still required for personal records.

Capabilities are granular at module/property/object boundaries, rather than a configurable permission for every action in the updated brief. Per-action policies such as approval-only `refunds.approve` require further explicit policy mapping and tests before claiming that finer model.

Tests must cover every role against own and foreign property collections, substituted document/invoice/payment/ticket IDs, mixed-role users, revoked/expired sessions and keys, and cross-organisation SQL context. See [SECURITY_TEST_RESULTS.md](SECURITY_TEST_RESULTS.md). UI visibility is supplementary to service and database controls.
